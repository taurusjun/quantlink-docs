## 1. 背景

当前系统已经接入：

```text
SimLocal
SimNow
SimShengli
SimVenue
```

并且存在两个互相冲突的交互假设：

```text
1. 顶部控件看起来像“全局场所过滤器”
2. 实际只有手工单、期权链等少数页面读取它
```

更严重的是，“当前交易账户”这个说法把以下概念混在一起：

```text
登录用户
交易账户 / 资金账户
柜台 / 交易所
ORS 执行实例
策略部署账户
页面查看范围
```

本设计明确：

> 行情和下单都跟着柜台（交易所）走；账户与柜台 1:1；登录用户与交易账户不是同一个概念。

---

## 2. 核心决策

### 2.1 柜台是执行边界

```text
柜台（Counterparty / Exchange）
  ├─ 行情
  ├─ 下单通道
  ├─ 撤单通道
  ├─ 回报 / 成交通道
  ├─ 账户（1:1）
  ├─ ORS（1:1 账户）
  ├─ 交易日历 / 交易时段
  ├─ 风控参数
  └─ 对账范围
```

切换柜台时，以上内容必须整体切换，不能只切换页面标题或账户显示。

### 2.2 账户与柜台 1:1

v1 不变量：

```text
1 柜台 = 1 账户
1 账户 = 1 ORS
1 ORS = 1 Runtime Agent
1 策略部署 = 1 ORS / 1 账户
```

账户不是独立于柜台的全局对象，不能出现：

```text
当前柜台 = SIMVENUE
当前账户 = SIMLOCAL-001
```

### 2.3 登录用户与交易账户分离

```text
登录用户：test_admin
权限范围：SIMLOCAL / SIMVENUE / SimNow
当前柜台：SIMVENUE
交易账户：SIMVENUE-001（由柜台决定）
```

登录用户可以是管理员、交易员或只读用户；交易账户是柜台下的业务对象。

### 2.4 顶部选择器叫“当前柜台”

不使用“当前交易账户”作为全局概念。

顶部选择器：

```text
当前柜台 [SIMVENUE · SIMVENUE-001 · RUNNING ▼]
```

它表示完整的执行上下文：

```text
Counterparty + Account + ORS + MarketData + OrderRoute + Calendar
```

### 2.5 页面范围与柜台选择分离

```text
顶部当前柜台：执行上下文，必须具体
页面范围：查看范围，可以是当前柜台或全部柜台
```

订单、持仓、策略等页面可以在“当前柜台 / 全部柜台”之间切换；下单动作只允许具体柜台。

## 3. 概念模型

| 概念 | 说明 | 归属 |
|---|---|---|
| 登录用户 User | 操作者身份 | 跨柜台 |
| 柜台 Counterparty | 接入通道/交易所执行边界 | 主分区 |
| 账户 Account | 柜台下的交易账户 | 1:1 柜台 |
| ORS | 账户的执行实例 | 1:1 账户 |
| Agent | 托管 ORS 和策略进程的主机代理 | 1:1 ACTIVE ORS |
| 交易所 Exchange | 合约属性；v1 与柜台一起展示 | 柜台/合约 |
| 行情 MarketData | 柜台行情流 | 1:1 柜台 |
| 策略 Strategy | 业务策略定义 | 可绑定多个部署 |
| 部署 Deployment | 策略在某 ORS 上的一次执行 | 1:1 ORS |
| 页面范围 PageScope | 数据页面的查询条件 | 页面状态 / URL |

## 4. 顶部栏设计

### 4.1 布局

```text
quantlink-fin | SHADOW | 登录: test_admin | 当前柜台: SIMVENUE ▼
              | 系统连接: UP | 只减仓 | 紧急操作
```

不提供“当前交易账户”独立下拉框。

### 4.2 柜台下拉内容

```text
SimLocal
  SIMLOCAL-001 · SIMLOCAL · RUNNING

SimVenue
  SIMVENUE-001 · SIMVENUE · RUNNING

SimNow
  TEST-001 · SIMNOW · STOPPED

SimShengli
  TEST-SHENGLI · SIMSHENGLI · OFFLINE
```

每项展示：

```text
账户
柜台/交易所
ORS 状态
行情状态
```

不可用柜台置灰，并显示原因。

### 4.3 切换语义

切换柜台时原子更新：

```text
marketDataScope     当前柜台行情
accountId           柜台绑定账户
orsId               账户绑定 ORS
orderChannel        下单通道
updateChannel       回报通道
tradeChannel        成交通道
calendar            柜台交易日历
riskLimits          柜台级风控
reconciliationScope 柜台级对账
```

切换后：

- 顶部显示新柜台
- 手工单账户/ORS 只读更新
- 行情 ticker 切换到新柜台
- 订单 / 持仓默认范围切换到新柜台
- 策略部署页面筛选到当前柜台，但不会改变已有部署

### 4.4 防误操作

- 手工单表单有未提交内容时，切换柜台必须确认
- 确认文案必须列出旧/新柜台和账户
- 不允许静默 fallback 到其他柜台
- 柜台 STOPPED/OFFLINE 时不能下单
- 切换柜台不能改变任何已有策略部署

## 5. 页面设计

### 5.1 交易页面

#### 手工下单 / 期权链

```text
当前柜台：SIMVENUE
交易账户：SIMVENUE-001（只读）
ORS：ors-simvenue-001（只读）
行情：SIMVENUE
```

用户只选择合约、方向、价格、数量，不再单独选择账户。

提交确认必须显示：

```text
柜台 SIMVENUE
账户 SIMVENUE-001
ORS ors-simvenue-001
合约 ag2612
方向 买入
价格 11800
数量 1
```

#### 策略页面

策略部署必须显式显示：

```text
策略：TEST-STRAT-PAIR-01
柜台：SIMLOCAL
账户：SIMLOCAL-001
ORS：ors-simlocal-001
状态：ACTIVE
```

顶部当前柜台只用于筛选页面，不改变策略执行账户。

### 5.2 数据页面

订单 / 成交 / 持仓：

```text
范围：[当前柜台 ▼] [全部柜台] [SimNow] [SimVenue]
策略：[全部 ▼]
交易所：[全部 ▼]
状态：[全部 ▼]
```

默认：

```text
订单 / 成交 / 持仓：当前柜台
监控 / 柜台总览：全部柜台
管理页面：全部柜台，不受顶部影响
```

“全部柜台”是只读范围：

- 可以查看聚合数据
- 可以跨柜台筛选
- 不能直接下单
- 下单入口必须提示选择具体柜台

### 5.3 管理页面

新增一级菜单：

```text
接入管理
  ├─ 柜台总览
  ├─ 账户管理
  ├─ ORS / Agent
  ├─ 通道与路由
  ├─ 行情源
  └─ 对账与健康
```

柜台总览卡片：

```text
SimVenue
  status: RUNNING
  account: SIMVENUE-001
  ORS: ors-simvenue-001
  market age: 20ms
  recon: PASS
  orders: 0
  last error: —
```

点击“进入交易”设置顶部当前柜台；管理页本身不依赖当前柜台。

## 6. 数据模型

### 6.1 目标模型

```text
user
  user_id
  username

user_account_permission
  user_id
  account_id
  role          TRADER / VIEWER / ADMIN

counterparty
  id
  name
  kind          CTP / SIM / REPLAY
  exchange      SHFE / DCE / CZCE / CFFEX / SIM
  environment   SHADOW / LIVE
  status
  calendar_mode REAL / ALWAYS_ON
  md_channel / md_stream
  metadata_json

account
  id
  counterparty_id   UNIQUE (v1)
  broker_account
  investor_id
  balance / available / margin

ors_instance
  ors_id
  counterparty_id
  account_id        UNIQUE (v1)
  agent_id          UNIQUE (v1)
  status
  order/cancel/update/trade/md channel + stream
  fencing_token

strategy_deployment
  strategy_id
  target_ors_id
  target_agent_id
  account_id
  generation
  desired_state / actual_state
```

### 6.2 与现有表的关系

当前字段可以渐进演进：

```text
venue_configs.id        → counterparty.id
accounts.venue_id       → account.counterparty_id
ors_instances.venue_id  → ors.counterparty_id
orders.venue            → orders.counterparty_id（订单快照）
```

v1 可以保留 `venue_id` 物理字段，但 UI/API 语义统一为 `counterparty`。

### 6.3 前端状态

```ts
type CounterpartyContext = {
  counterpartyId: string
  exchange: string
  accountId: string
  orsId: string
  status: 'RUNNING' | 'STOPPED' | 'OFFLINE'
  mdStream: number
  orderStream: number
}

type PageScope = {
  counterpartyId?: string
  accountId?: string
  exchange?: string
  strategyId?: string
}
```

- `CounterpartyContext`：顶部选择器
- `PageScope`：订单/持仓/监控页面
- `user`：登录身份
- `lastCounterpartyId`：用户偏好，仅作为默认值

## 7. API 设计

### 7.1 柜台与上下文

```text
GET /api/v1/execution/contexts
  → counterpartyId / accountId / orsId / status / channels

GET /api/v1/me/counterparties
  → 当前用户有权限的柜台
```

### 7.2 数据过滤

```text
GET /api/v1/orders?counterpartyId=&accountId=&exchange=&strategyId=&status=
GET /api/v1/trades?counterpartyId=&accountId=&exchange=
GET /api/v1/positions?counterpartyId=&accountId=
GET /api/v1/strategies?counterpartyId=&accountId=
GET /api/v1/monitoring/summary?groupBy=counterparty
```

不允许前端拉全量后在浏览器过滤。

### 7.3 下单

```json
{
  "counterpartyId": "SIMVENUE",
  "accountId": "SIMVENUE-001",
  "orsId": "ors-simvenue-001",
  "instrumentId": "ag2612",
  "side": "B",
  "price": 11800,
  "qty": 1
}
```

服务端校验：

```text
counterparty.account_id == request.accountId
account.ors_id == request.orsId
instrument.exchange compatible with counterparty
user has permission on account
```

## 8. 行情与路由隔离

### 8.1 行情

每个柜台必须使用独立行情流，或消息中携带 `counterpartyId`。

当前 SimLocal 与 SimVenue 都使用 `md_stream=1001`，在多柜台场景下存在歧义。目标：

```text
SIMLOCAL  md_stream = 1001
SIMVENUE  md_stream = 1001（如果数据源相同，仍需带 counterpartyId）
SimNow    md_stream = 1100
SimShengli md_stream = 1110
```

前端行情 ticker 只订阅当前柜台；监控页可以展示全部柜台。

### 8.2 订单

```text
当前柜台
  → account
  → 唯一 ACTIVE ORS
  → order channel/stream
```

不允许：

```text
当前柜台 SIMVENUE
订单发到 SIMLOCAL 的 2120
```

## 9. 策略与多柜台

- 策略部署时显式绑定柜台/账户/ORS
- 顶部当前柜台不改变已有策略
- 同一策略不能同时部署到多个 ORS
- 跨柜台套利必须显式配置两条腿
- 跨柜台策略必须在部署摘要中展示两个柜台、两个账户、两个 ORS
- 任一柜台断线时按策略配置 fail-closed，不自动切柜台

## 10. 监控与对账

### 监控

默认展示全部柜台：

```text
柜台级：
  connected / market age / order rate / reject rate
  ORS status / agent status / queue depth / backpressure

账户级：
  available / margin / PnL / positions

策略级：
  deployment / actual state / recon gate
```

点击柜台卡片将页面范围设为该柜台。

### 对账

每个柜台独立：

```text
orders
trades
positions
account
reconciliationGate
```

不能使用全局对账结果放行所有柜台。

## 11. 权限与审计

- 登录用户与交易账户分离
- 用户只能看到有权限的柜台/账户
- 交易员只能对授权账户下单
- 管理员可以跨柜台管理
- 切换柜台、部署策略、紧急操作记审计
- 下单确认和日志必须带：
  `counterpartyId / accountId / orsId / clientOrderId / requestId`

## 12. 迁移与实施顺序

### Phase 1：术语与顶部选择器

- UI 将“场所/账户”改为“当前柜台”
- 顶部展示 `柜台 · 账户 · ORS · 状态`
- 保留现有 `venue_id` 字段
- 切换柜台联动手工单、期权链、行情 ticker

### Phase 2：页面范围

- 订单、成交、持仓、策略增加柜台范围过滤器
- 支持“当前柜台 / 全部柜台”
- 过滤器写入 URL
- 管理页面移除顶部柜台依赖

### Phase 3：柜台总览

- 新增柜台总览页
- 展示柜台、账户、ORS、行情、对账、健康
- 点击进入交易

### Phase 4：权限与多柜台路由

- 用户-账户权限
- 柜台级风控/日历
- 行情流隔离
- 多柜台监控与对账

### Phase 5：跨柜台策略

- 显式多腿配置
- 跨柜台风险与对账
- 不自动 failover

---

## 13. 验收标准

```text
[ ] 顶部只有“当前柜台”，没有“当前交易账户”
[ ] 切换 SIMVENUE 后，行情、账户、ORS、下单通道、日历一起切换
[ ] 切换柜台不会改变已有策略部署
[ ] 订单页面可选择当前柜台/全部柜台
[ ] 全部柜台范围不能直接下单
[ ] 登录用户与交易账户在 UI/API 中分离
[ ] 1 柜台 = 1 账户 = 1 ORS 不变量可验证
[ ] 每个柜台行情/订单/回报通道唯一或带 counterpartyId
[ ] 柜台级对账失败只阻塞该柜台
[ ] 跨柜台策略必须显式配置
```

## 14. 待交易员确认的问题

1. 顶部是否接受“当前柜台”这个名称，还是更习惯“当前交易所/当前通道”？
2. 交易员是否需要在同一页面同时盯多个柜台，还是切换单一柜台即可？
3. 手工单是否允许临时选择非当前柜台，还是必须切顶部柜台？
4. 订单/持仓默认看当前柜台还是全部柜台？
5. 跨柜台策略是否在 v1 范围外？
6. 切换柜台时，未提交订单应清空还是保留草稿？
7. 管理员和交易员是否共用同一套顶部栏，还是管理员默认全部柜台只读？
