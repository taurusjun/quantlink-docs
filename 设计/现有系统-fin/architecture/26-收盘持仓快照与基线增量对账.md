# 收盘持仓快照与基线增量对账设计

> 状态：设计确认，待实现  
> 适用：`quantlink-fin` 管理面、Runtime Runner、CTP Adapter、SimVenue  
> 目标：把“当前持仓 vs 全部历史成交”改为“收盘基线 + 基线后成交增量”

## 1. 背景

当前管理面存在两类问题：

1. 策略持仓、账户持仓、历史成交分别来自不同链路，时间上不是严格同步。
2. 对账直接使用：

   ```text
   当前持仓 == 本地 trades 全部历史净额
   ```

   这对以下场景不成立：

   - CTP 隔夜仓没有本地成交流水
   - 账户新接入、历史成交未导入
   - 策略持仓已平，但本地历史成交净额不为 0
   - 同一账户下多个策略/手工单混合持仓

老交易系统已经采用每日初始化的模型：

- ORS 启动加载 `position.csv`
- 登录后查询 CTP `ReqQryInvestorPosition`
- 用 CTP 持仓替换 `mapContractPos`
- 查询完成后才设置 `m_connected=true`
- Pair 策略启动读取 `daily_init.<strategyID>`

新系统应对齐这个模型：**每天收盘保存权威持仓快照，盘中只对账基线后的增量。**

## 2. 目标与非目标

### 目标

- 每个收盘时点保存一份不可变的账户总持仓快照。
- 每个收盘时点保存每个策略的 `daily_init` 数据快照。
- 快照必须带策略版本、deployment、数据源时间。
- 对账按“账户 + 合约 + 多空分别”进行。
- 支持账户/策略/手工/UNASSIGNED 归属校验。
- 支持 CTP/SimVenue 查询失败、迟到成交、重复任务、版本切换。
- Runner 重启时能按正确策略版本加载 daily state。
- 为开仓门禁提供可追溯、可恢复的基线。

### 非目标

- 不使用历史成交反推所有隔夜仓。
- 不覆盖已经 READY 的历史快照。
- 不把管理面内存状态作为权威持仓。
- 不通过关闭对账门禁来“修复”账实差异。

## 3. 数据权威定义

按优先级：

```text
账户总持仓：CTP / SimVenue 查询结果
策略归属：strategy_positions（由策略成交账本维护）
daily_init：strategy_daily_state（Pair 策略收盘保存）
手工仓：手工簿
差额：UNASSIGNED，不允许静默并入某个策略
```

策略持仓的日常维护由：

```text
Aeron trade/update
  -> ExecutionLedgerService
  -> StrategyPositionService.applyFill
  -> strategy_positions
```

完成。

## 4. 收盘采集时序

### 4.1 标准时序

```text
收盘时间到达
  -> 停止新开仓/执行收盘平仓
  -> 等待订单、成交、持仓消费者 drain
  -> 等待 CTP 持仓查询完成（bIsLast）
  -> 固定 cutoff_at
  -> 读取 strategy_positions / strategy_daily_state
  -> 写入账户总持仓快照
  -> 写入策略持仓快照
  -> 写入 daily_init 快照
  -> 账户/策略/手工/UNASSIGNED 对账
  -> READY 或 MISMATCH
  -> READY 时生成下一周期 baseline
```

关键点：**快照不是在 15:05 定时器触发时立即写入，而是在 CTP 查询和成交消费链路都完成之后写入。**

### 4.2 采集屏障

采集前必须满足：

```text
1. 收盘平仓流程完成
2. 没有未处理的订单/成交消息
3. CTP ReqQryInvestorPosition 已返回 bIsLast
4. 本地 positions/strategy_positions 消费者已追到对应 checkpoint
5. strategy_daily_state 已保存
```

如果任一项不满足：

```text
run.status = FAILED / STALE
不更新 baseline
保留上一份 READY 快照
告警
```

### 4.3 日盘/夜盘

```text
日盘收盘：15:05 后采集
夜盘收盘：02:35 后采集
```

`trading_day` 必须来自交易日历，不能用简单的 `LocalDate.now()` 代替。  
夜盘归属按交易日历定义，避免把周五夜盘归到周五。

## 5. 时间字段

所有数据库时间使用 `TIMESTAMPTZ`，显示时转换为 `Asia/Shanghai`。

| 字段 | 含义 | 用途 |
|---|---|---|
| `trading_day` | 交易日 | 快照归属 |
| `session_type` | `DAY` / `NIGHT` | 日盘/夜盘 |
| `cutoff_at` | 本次对账业务截止时间 | 划分基线前后成交 |
| `started_at` | 采集任务开始 | 运维 |
| `completed_at` | 采集任务完成 | 运维 |
| `source_observed_at` | CTP/SimVenue 数据实际观测时间 | 判断数据是否过期 |
| `strategy_saved_at` | strategy_daily_state 保存时间 | 判断 daily_init 是否及时 |
| `captured_at` | 管理系统写入快照时间 | 审计 |
| `consumer_sequence` | 成交消息消费位点（可选但推荐） | 严格边界 |

约束：

```text
source_observed_at >= cutoff_at
strategy_saved_at >= cutoff_at
captured_at >= source_observed_at
```

`cutoff_at` 不是定时器计划时间，而是**数据屏障完成后的统一切点**。

## 6. 数据模型

### 6.1 快照批次

```sql
CREATE TABLE position_snapshot_run (
    run_id              UUID PRIMARY KEY,
    trading_day         DATE NOT NULL,
    session_type        TEXT NOT NULL CHECK (session_type IN ('DAY', 'NIGHT')),
    run_key             TEXT NOT NULL,
    status              TEXT NOT NULL,
    cutoff_at           TIMESTAMPTZ,
    started_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    completed_at        TIMESTAMPTZ,
    source              TEXT NOT NULL,
    issue_count         INTEGER NOT NULL DEFAULT 0,
    issues_json         JSONB NOT NULL DEFAULT '[]'::jsonb,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (trading_day, session_type, run_key)
);
```

建议 `run_key`：

```text
trading_day:session_type:cutoff_at_bucket
```

支持幂等重试，不重复生成同一次收盘快照。

状态：

```text
CAPTURING
DRAINING
QUERYING
SNAPSHOTTING
VALIDATING
READY
MISMATCH
FAILED
STALE
```

### 6.2 快照头

```sql
CREATE TABLE position_snapshot (
    snapshot_id         UUID PRIMARY KEY,
    run_id              UUID NOT NULL REFERENCES position_snapshot_run(run_id),
    scope_type          TEXT NOT NULL CHECK (
                            scope_type IN ('ACCOUNT', 'STRATEGY', 'MANUAL', 'UNASSIGNED')
                        ),
    scope_id            TEXT NOT NULL,
    account_id          TEXT,
    strategy_version    TEXT,
    deployment_id       BIGINT,
    deployment_generation BIGINT,
    config_hash         TEXT,
    source              TEXT NOT NULL,
    as_of               TIMESTAMPTZ NOT NULL,
    source_observed_at  TIMESTAMPTZ,
    captured_at         TIMESTAMPTZ NOT NULL DEFAULT now(),
    total_long          INTEGER NOT NULL DEFAULT 0,
    total_short         INTEGER NOT NULL DEFAULT 0,
    status              TEXT NOT NULL,
    UNIQUE (run_id, scope_type, scope_id)
);
```

说明：

- `ACCOUNT`：账户总持仓（CTP/SimVenue）
- `STRATEGY`：策略归属持仓
- `MANUAL`：手工簿持仓
- `UNASSIGNED`：差额归属

策略版本字段只对 `STRATEGY` 快照有意义；其他 scope 可以为空。

### 6.3 快照明细

```sql
CREATE TABLE position_snapshot_item (
    snapshot_id         UUID NOT NULL REFERENCES position_snapshot(snapshot_id),
    instrument_id       TEXT NOT NULL,
    exchange            TEXT NOT NULL,
    today_long          INTEGER NOT NULL DEFAULT 0,
    today_short         INTEGER NOT NULL DEFAULT 0,
    yesterday_long      INTEGER NOT NULL DEFAULT 0,
    yesterday_short     INTEGER NOT NULL DEFAULT 0,
    long_qty            INTEGER NOT NULL DEFAULT 0,
    short_qty           INTEGER NOT NULL DEFAULT 0,
    avg_price           NUMERIC(20, 6) NOT NULL DEFAULT 0,
    PRIMARY KEY (snapshot_id, instrument_id, exchange)
);
```

### 6.4 strategy daily_init 快照

对应老系统：

```text
../data/daily_init.<strategyID>
```

```sql
CREATE TABLE strategy_daily_init_snapshot (
    snapshot_id          UUID PRIMARY KEY,
    run_id               UUID NOT NULL REFERENCES position_snapshot_run(run_id),
    strategy_id          TEXT NOT NULL,
    strategy_version     TEXT NOT NULL,
    deployment_id        BIGINT,
    deployment_generation BIGINT,
    config_hash          TEXT,
    trading_day          DATE NOT NULL,
    session_type         TEXT NOT NULL,
    avg_px               NUMERIC(20, 6),
    ytd1                 INTEGER,
    today1               INTEGER,
    ytd2                 INTEGER,
    px1                  NUMERIC(20, 6),
    px2                  NUMERIC(20, 6),
    max_pnl              NUMERIC(20, 6),
    pnl                  NUMERIC(20, 6),
    strategy_saved_at    TIMESTAMPTZ,
    source               TEXT NOT NULL,
    as_of                TIMESTAMPTZ NOT NULL,
    captured_at          TIMESTAMPTZ NOT NULL DEFAULT now(),
    UNIQUE (run_id, strategy_id, strategy_version, deployment_id)
);
```

`ytd1`、`today1`、`ytd2` 等字段保持老 `daily_init` 语义，不做重新解释。

### 6.5 基线

```sql
CREATE TABLE position_baselines (
    baseline_id         UUID PRIMARY KEY,
    scope_type          TEXT NOT NULL CHECK (scope_type IN ('ACCOUNT', 'STRATEGY')),
    scope_id            TEXT NOT NULL,
    instrument_id       TEXT NOT NULL,
    snapshot_id         UUID NOT NULL REFERENCES position_snapshot(snapshot_id),
    as_of               TIMESTAMPTZ NOT NULL,
    effective_from      TIMESTAMPTZ NOT NULL,
    effective_until     TIMESTAMPTZ,
    source              TEXT NOT NULL,
    created_at          TIMESTAMPTZ NOT NULL DEFAULT now()
);
```

基线不重复保存数量，数量从快照明细读取。

基线生效规则：

- 新 READY 快照生成后，旧基线设置 `effective_until`
- 新基线 `effective_from = cutoff_at`
- 历史基线不回写、不删除
- 对账取当前有效基线

## 7. 策略版本

策略快照和 daily_init 必须记录：

```text
strategy_id
strategy_version
deployment_id
deployment_generation
config_hash
```

版本来源优先级：

```text
1. 实际运行的 strategy_deployments.strategy_version
2. deployment generation / config_hash
3. 无运行部署时使用 strategies.current_version
```

不能只看 `strategies.current_version`，因为可能：

```text
数据库 current_version = v0.3
实际运行 deployment = v0.2
```

快照记录“实际运行版本”。

### 版本切换原则

版本变化不等于持仓清零：

```text
v0.2 持有 ag2612 2 手
升级到 v0.3
这 2 手仍然属于该策略
```

所以：

- `strategy_positions` 仍按策略/账户/合约保存持仓
- 版本只作为快照、daily_init 和审计字段
- 基线仍按策略/账户/合约生效

Runner 启动时读取 daily state 要带版本：

```text
GET /api/v1/strategies/{id}/daily-state
    ?version=v0.2
    &deploymentId=25
```

不能无版本取“最新一条”。

## 8. 对账公式

### 8.1 收盘归属校验

按 `account_id + instrument_id`，分别核对多头和空头：

```text
ACCOUNT.long_qty
  ==
sum(STRATEGY.long_qty)
 + MANUAL.long_qty
 + UNASSIGNED.long_qty

ACCOUNT.short_qty
  ==
sum(STRATEGY.short_qty)
 + MANUAL.short_qty
 + UNASSIGNED.short_qty
```

不能只比较净额，因为：

```text
策略 A long 5
策略 B short 5
```

净额为 0，但账户可能实际持有 `long 5 + short 5`。

### 8.2 基线增量对账

账户：

```text
current_account_position
  ==
account_baseline
 + sum(account trades where created_at > baseline.as_of)
```

策略：

```text
current_strategy_position
  ==
strategy_baseline
 + sum(strategy trades where created_at > baseline.as_of)
```

### 8.3 收盘快照校验

快照生成后同时校验：

```text
ACCOUNT == STRATEGY + MANUAL + UNASSIGNED
```

正差额表示账户多出来的持仓，进入显式 UNASSIGNED 桶：

```text
run.status = READY_WITH_UNASSIGNED
issues_json 记录未分配数量
```

负差额表示策略/手工归属超过柜台持仓，无法用 UNASSIGNED 桶吸收：

```text
run.status = MISMATCH
```

不能静默把任何差额并入策略，也不能在负差额时生成干净基线。

## 9. 失败与异常

### 9.1 CTP 查询失败

```text
run.status = FAILED
不生成新 baseline
保留上一份 READY 快照
告警
```

### 9.2 成交消费者延迟

如果 CTP 已返回，但 `orders/trades/strategy_positions` 还没追平：

```text
run.status = DRAINING / STALE
```

继续等待或标记 FAILED，不写 READY。

### 9.3 daily_init 过期

```text
strategy_saved_at < cutoff_at - 120s
```

标记：

```text
STRATEGY_DAILY_STATE_STALE
```

daily_init 过期记录为 warning，不直接阻断账户/策略持仓基线；但需要告警并禁止按旧 daily_init 恢复 Runner。收盘任务内部有 120 秒容差，覆盖 15:05 保存、15:06 采集的正常顺序。

### 9.4 迟到成交

如果一笔成交在快照完成后到达，且时间属于 `cutoff_at` 之前：

- 不修改历史快照
- 生成新版本快照，或
- 标记 late event 并重新对账

保留：

```text
superseded_by
late_event_at
consumer_sequence
```

## 11. 定时任务

建议与现有费率刷新分离或串联：

```text
15:06 日盘收盘快照（等 daily_init 落库）
02:36 夜盘收盘快照
```

流程：

```text
1. 触发 capture
2. 等 CTP bIsLast
3. 写入快照
4. 校验
5. READY 后生成基线
6. 失败时告警，不更新基线
```

复用现有 CTP Adapter 会话，不允许新建 CTP 登录。

## 12. Runtime 门禁与延迟容忍

### 12.1 职责边界

管理面和运行时的职责必须分开：

```text
管理面：
  收盘快照
  基线生成
  异步对账
  持续差异告警和审计

运行时：
  本地成交账本
  pending fills
  本地基线 + 本地增量
  开仓风险判断
```

运行时**不能每笔开仓同步查询管理面数据库**。  
管理面快照只用于：

```text
1. Runner 启动 bootstrap
2. 收盘基线
3. 漂移告警
4. 持续异常阻断
```

### 12.2 正常延迟不阻断开仓

以下情况属于正常链路延迟：

```text
成交已由 Aeron 到达 Runner
管理面的 trades/positions 消费者还没消费
reconciliation_status 还在上一轮
```

这种延迟不能直接阻止 OPEN。运行时应该使用：

```text
本地基线
+ 本地 pending fills
+ 本地成交增量
```

计算当前持仓和风险。

### 12.3 什么情况下阻断 OPEN

建议分级：

```text
WARN：
  管理面延迟、单次对账失败
  → 记录告警，允许 OPEN

DEGRADED：
  连续失败未超过窗口
  → 记录告警，允许 OPEN
  → 页面提示对账延迟

BLOCK OPEN：
  连续 N 个周期持续不一致
  或柜台权威持仓与本地持续不一致
  或运行时本地风险快照过期
  → 拒绝新开仓
```

建议默认值：

```text
正常刷新：5 秒
管理面宽限：30–60 秒
连续失败：3 个周期或 60 秒
```

`CLOSE`、`CANCEL`、`REDUCE` 永远允许，不能因为管理面延迟阻止降风险。

### 12.4 开仓判定

```text
OPEN 允许：
  1. 本地基线存在
  2. 本地 pending fills 可计算
  3. 本地风险快照新鲜
  4. 未超过连续不一致窗口
  5. 账户/策略/柜台均无持续性错误
```

不能使用：

```text
管理面每 5 秒刷新一次 → 每笔 OPEN 等待该刷新
```

否则一次消费者延迟就会误伤正常策略。

### 12.5 门禁状态字段

```text
scope
passed
last_success_at
consecutive_failures
issues
baseline_as_of
degraded
degraded_since
```

页面和日志要区分：

```text
DELAYED  —— 数据还没到，允许交易
MISMATCH —— 数据到了但不一致，持续超窗口后阻断
STALE    —— 运行时自身风险快照过期，阻断
```

### 12.6 现有代码的调整方向

当前 `AeronOrderGateway` 已经在本地维护 position book，但还需要明确：

- 启动时从最新 READY 快照 bootstrap
- 运行中用 Aeron 成交增量更新
- 管理面持仓只做 drift 告警
- OPEN 门禁使用本地基线和本地增量
- 只有持续差异才读取并阻断

这样正常几秒的延迟不会阻止开仓，持续账实错误仍然会阻断新开仓。

## 13. 保留与审计

- 快照按交易日保留，不覆盖
- 至少保留一个完整交易年度
- 大盘/归档前保留 `run_id`、`cutoff_at`、`source`
- 任何手工基线修复必须有审计记录
- 数据库只增不改已 READY 快照

## 15. 验收标准

### 快照

- 日盘、夜盘各生成一份 run
- CTP 未完成查询时不生成 READY
- 快照包含账户总持仓、策略持仓、手工/未分配
- 快照包含策略版本、deployment、时间字段
- 重复执行同一 `run_key` 不产生重复数据

### 对账

- 多空分别校验
- 账户 = 策略 + 手工 + 未分配
- 基线之后成交才能计入增量
- 版本切换不清空策略持仓
- CTP 失败不覆盖旧基线
- 迟到成交有审计和处理路径

### 门禁

- 无 READY 基线时，OPEN 被拒绝
- 基线正常后，OPEN 恢复
- 管理面正常延迟不阻止 OPEN
- 连续不一致超过窗口后才阻止 OPEN
- CLOSE/CANCEL/REDUCE 不受对账延迟影响
- 持续 MISMATCH 告警，不静默放行

## 16. 关键设计结论

```text
每日收盘保存不可变快照
账户总持仓和策略 daily_init 分开保存
快照必须包含版本和多个时间字段
对账必须多空分别、账户/策略/手工/未分配分层
基线只引用 READY 快照
基线之后只计算增量
CTP 查询失败不能覆盖上一份基线
```

这份设计替代当前的“用全量历史成交反推持仓”逻辑。
