## 1. 目标

```text
公司 ORS 的业务行为保持不变
  +
SHM Request/Response 替换为 Aeron
  +
account query + 状态文件读写改为 CTP 查询
（配置文件的读取保留；position.csv / contract 状态文件不保留）
  +
SDK 只做通信，不持有订单状态
```

ORS v4 仍然是：

```text
一个进程 = 一个 CTP 账户
一张账户级订单 map
一套账户级 RMS
一个 TraderApi / MdApi 会话
```

不按交易所拆分订单管理。

---

## 2. 不做什么

- 不沿用 v3 的 `TradingChannel`、`OrderRegistry`、`FillLedger`、平仓预扣
- 不把 v3 `CtpAdapter` 的 `NEW/ACK/PARTIAL` 状态机当作 ORS v4 核心
- 不在 SDK 里维护订单状态
- 不重写公司 ORS 的订单、撤单、RMS、终态逻辑；只替换状态数据来源
- 不做多 adapter 单进程路由
- 不在本次方案里改 SimVenue/FastTrade 的业务逻辑；它们按 contract 1.0.0 迁移

## 4. 核心改造点

### 4.1 把 SHM 从 `ORSServer` 中拿掉

公司 ORS 当前有三处 SHM 耦合：

```text
ORSServer 构造函数：
  createClientStore / createRequestClients / createResponseClient

ORSServer::Start：
  startMonitorAsyncORSRequest

ORSServer::PushUpdate：
  m_responseInterface->enqueue
```

改造为 transport 接口，不改变订单逻辑：

```cpp
class OrsTransport {
 public:
  virtual ~OrsTransport() = default;
  virtual void sendResponse(const ResponseMsg&) = 0;
  virtual void sendMarketData(const MarketUpdateNew&) = 0;
  virtual void sendSession(const SessionEvent&) = 0;
};
```

`ORSServer` 只保留：

```text
ProcessRequest(RequestMsg*)
PushUpdate(ResponseMsg*)
CTP callbacks
订单 map / RMS / position
```

`PushUpdate` 从 `m_responseInterface->enqueue` 改为 `transport_->sendResponse(*resp)`。

### 4.2 输入改为 Aeron subscription

新增 `AeronOrsTransport`：

```text
Aeron REQUEST stream
  -> decode OrsRequest
  -> ORSServer::ProcessRequest

Aeron REQUEST stream（按 SBE templateId 分流）
  -> templateId == AccountQuery
  -> ORSServer::QueryAccount

Aeron ACCOUNT stream
  <- AccountSnapshot

Aeron CONTROL stream
  -> ClientRegister / ClientRegisterResponse
  -> 分配 clientId

Aeron MARKET_DATA / RESPONSE / SESSION
  <- encode and publish
```

`ClientRegister` 是替换公司 SHM ClientStore 的控制路径，不改变订单/RMS 逻辑。OrderID 仍按
`clientId * 1_000_000 + orderCount` 生成。

请求处理线程与 CTP 回调线程的边界按公司 ORS 原有语义保留；不要为了 Aeron 把订单处理拆成多线程状态机。

### 4.3 MDHandler 改为输出 sink

公司 `MDHandler::ProcessMDUpdate` 当前直接写 `MarketDataShmWriter`。  
改为：

```text
ProcessMDUpdate
  -> 更新 m_timestamp/m_seqnum
  -> transport_->sendMarketData(*update)
```

MD 的 `m_symbol`、`m_exchTS`、`m_timestamp`、`m_seqnum`、20 档结构按公司 `MarketUpdateNew` 保留，不自造 v3 `MarketData` 语义。

### 4.4 account / position / instrument query

采用 `quantlink-trading/ors/China` 生产 ORS 的内联查询模式：

```text
ReqQryInstrument / ReqQryInvestorPosition / ReqQryTradingAccount
  -> ORSServer 成员函数
OnRspQry...
  -> ORSServer CTP 回调
```

不新增独立的 `QueryService` 或 `QueryCoordinator`。只抽：

```text
QueryMapping       纯字段映射，返回 AccountSnapshot / PositionRow
AccountQueryState  account query 的 pending、requestId 关联和节流
```

### 4.4.1 QueryMapping

`QueryMapping` 是纯函数集合，不发送 CTP 请求、不保存请求状态、不处理回调：

```cpp
AccountSnapshot mapAccountSnapshot(
    const CThostFtdcTradingAccountField& row,
    uint64_t requestId,
    const OrsConfig& config);

PositionRow mapPositionRow(const CThostFtdcInvestorPositionField& row);

std::vector<PositionRow> mergePositionRows(std::vector<PositionRow> rows);
```

职责：

- CTP 定宽 `char[]` 转 `std::string`
- `DBL_MAX`、NaN 转 `0.0`
- 多空两条持仓行合并
- 只做字段转换，不决定 READY/FAILED，不重试

### 4.4.2 AccountQueryState

`AccountQueryState` 只保存 account query 的请求状态，不是返回值：

```cpp
class AccountQueryState {
 public:
  bool tryBegin(uint64_t requestId,
                std::chrono::steady_clock::time_point now,
                std::chrono::milliseconds timeout);
  void bindCtpRequest(int ctpRequestId);
  std::optional<uint64_t> requestIdFor(int ctpRequestId) const;
  std::optional<uint64_t> expire(std::chrono::steady_clock::time_point now);
  void finish();

 private:
  bool pending_{false};
  uint64_t requestId_{0};
  int ctpRequestId_{0};
  std::chrono::steady_clock::time_point lastSent_{};
  std::chrono::steady_clock::time_point deadline_{};
};
```

规则：

- `tryBegin` 检查 pending 和 1000 ms 间隔，设置 `deadline = now + timeout`；不满足返回 false，由 `ORSServer` 返回拒绝结果
- `bindCtpRequest` 保存 CTP `nRequestID` 与 SDK `requestId` 的对应
- `requestIdFor` 只在当前 pending 匹配时返回 requestId
- `expire(now)` 在 pending 超时后返回原 SDK requestId，并清空 pending；`ORSServer` 用它发送超时 `AccountSnapshot`
- `finish` 清空 pending，允许下一次查询
- 不发送 CTP 请求，不处理回调，不决定 READY/FAILED
- position/instrument 启动查询不使用这个状态，使用启动屏障和退避重试

超时规则：

```text
ORS_ACCOUNT_QUERY_TIMEOUT_MS = 5000
SDK requestTimeout          = 6000
```

ORS 在 `ReqQryTradingAccount` 成功后开始计时。超时后发送：

```text
AccountSnapshot.requestId = 原 SDK requestId
AccountSnapshot.errorCode = ORS_ACCOUNT_QUERY_TIMEOUT
AccountSnapshot.errorMsg  = "account query timeout"
```

超时后到达的 CTP 回调因 `requestIdFor` 已无匹配而丢弃。SDK 超时只让 SDK 自己报错，不能代替 ORS 清理 pending。

### 4.4.3 PositionTable 动态更新

`PositionTable` 不是启动快照，它必须承载 `mapContractPos` 的完整生命周期：

```text
启动/周期查询 OnRspQryInvestorPosition bIsLast
  -> replaceFromQuery(rows) 整表替换

下单前 SetCombOffsetFlag
  -> reserveForOrder(symbol, side, qty, exchange)
  -> 返回 offsetFlag + qtyType，并扣减对应 today/yesterday 可平数量

订单失败 / 撤单确认
  -> restoreOnFailure(orderInfo, response)
  -> 把预扣数量加回

成交确认
  -> applyTrade(orderInfo, response)
  -> OPEN 增加 today 持仓；CLOSE 不重复加（下单前已扣）
```

每种更新都必须和公司 ORS 使用同一把 `contractPosLock` 语义。查询整表替换时，旧表中不再出现的非零持仓被清除，不能保留幽灵持仓。

启动顺序按生产 ORS：

```text
login
  -> ReqQryInstrument
  -> OnRspQryInstrument bIsLast
  -> ReqQryInvestorPosition
  -> OnRspQryInvestorPosition bIsLast
  -> 整表替换 PositionTable
  -> READY
```

要求：

- 查询入口、`m_iRequestID`、`requestIdByCtpRequestId` 都留在 `ORSServer`
- 一个进程一个 TraderApi、一个 SPI，不增加第二套 query SPI
- 只查当前账户
- account query 有节流，不背靠背查询
- account query 失败只返回错误 snapshot，不改变订单状态、不影响 READY
- account snapshot 通过单独 Aeron stream 返回
- position/instrument 初始化使用 CTP 查询，不读 position.csv / contract 文件
- 不在 CTP 回调里 `usleep` 重试；重试由定时器/主循环调度，避免阻塞订单/成交回报
- 查询失败不能让 ORS 用旧文件或旧内存状态降级进入 READY
- 不把 account query 做成订单状态查询

### 4.5 公司订单行为保留

必须保持：

- `m_ordLocalMap` / `m_ordExchMap`
- 未知撤单返回 `CANCEL_ORDER_REJECT`
- 撤单拒绝后原订单继续
- 终态清理
- `NEW_ORDER_CONFIRM` / `TRADE_CONFIRM` / `ORDER_ERROR` 时序
- RMS 和撤单计数
- 旧 front/session 过滤
- OrderID 作为账户级订单主键

不要把 v3 的 `OrderUpdate.status` / `CancelState` 引入核心。

## 5. ORS 与 SDK 的接口

SDK 负责：

```text
Aeron 连接/重连
RequestMsg/ResponseMsg 编解码
OrderID 分配
请求/响应关联
超时
回调分发
```

SDK 不负责：

```text
订单状态
订单 map
RMS
预扣
终态判断
```

ORS 只接受 SDK 的请求，返回公司语义的响应。

## 6. 进程与部署

```text
一个 CTP 账户
  -> 一个 ORS v4 进程
  -> 一个 TraderApi 会话
  -> 一个 MdApi 会话
```

多账户：

```text
account-1 -> ors-1
account-2 -> ors-2
```

不共享订单 map，不做进程内多账户路由。

每个进程需要独立：

```text
ORS_ID
CTP 账户配置
trader/md flow path
日志路径
Aeron request/response stream
```

Aeron 目录可以共享，stream 不能冲突。

## 8. 测试与验收

### 核心行为

- 下单/撤单字段映射与公司 ORS 一致
- 未知撤单返回 `CANCEL_ORDER_REJECT`
- 撤单拒绝后订单继续有效
- 终态订单清理
- 成交先于终态
- 旧 front/session 回报丢弃
- RMS 拒单和订单状态不变
- account query 成功/失败
- account query 超时返回错误 `AccountSnapshot` 并清 pending
- 超时后迟到的 CTP 回调被丢弃
- instrument/position 查询初始化，无文件依赖
- 账户查询不影响 READY/订单状态

### 基础库与日志

- 生产代码无 `ILOG` / `StatsCollector` / 业务 `std::cerr`
- JSONL 每行可解析，字段符合事件字典
- 热点路径无逐 tick 日志，60 秒 metrics 正常
- RMS、订单状态逻辑未因库替换改变

### Transport

- Aeron back-pressure 不静默丢请求
- 断线重连
- response/orderId 关联
- 重复/乱序响应处理
- MD 不重复、不旧 tick 覆盖

### 集成

- ORS v4 + SDK + TradeBot
- ORS v4 + SimVenue + FastTrade
- 多账户多进程
- 交易时段 live lifecycle

## 9. 风险

- 公司 ORS 代码老，依赖 hftbase/SHM/RMS；解耦会碰大量旧代码
- `ResponseMsg.ExchangeOrderId` 是 `double`，不要随手改类型
- `StrategyID` 不在公司 `RequestMsg` 中；TradeBot 的 `OrderIDStrategyMap` 仍按 OrderID 归属
- CTP account/position/instrument query 有频率限制，必须节流
- 文件状态删除后，查询失败不能让 ORS 用旧文件或旧内存状态装作 READY
- MD 结构字段多，contract 1.0.0 必须按实际消费字段裁剪，不能直接照搬 v3 `MarketData`
- 如果 SDK 重发请求，ORS 必须按 OrderID/订单 map 做幂等或明确拒绝
- SimVenue/FastTrade 同时迁 contract 1.0.0，联调窗口要一起排
