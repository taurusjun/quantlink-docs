# 交易端改造方案（合并交易员评审 + UX 评审）

- 日期：2026-11-11
- 输入：
  - `docs/reviews/2026-11-11-trader-review.md`（交易员视角，30 条问题 + 23 条需求）
  - `docs/reviews/2026-11-11-ux-review.md`（UX 视角，6 P0 / 13 P1 / 10 P2）
- 目标：把两份评审合并成一份可执行、可验收、可分期的改造方案，消除重复项，明确先后顺序与依赖。
- 原则：
  1. **先让“不能交易”可见，再谈好看**。
  2. **管理面不计算**：敞口/限额/保证金等由运行体上报（AGENTS.md P0）。
  3. **单一事实来源**：策略状态、行情新鲜度、告警指纹各自只保留一套词表。
  4. **危险动作影响面可见**：撤多少单、平多少手、涉及哪个账户，必须写在确认框里。
  5. 沿用现有深色高密度视觉与 `ConfirmDialog`，不重做设计语言。

---

## 1. 两份评审的重叠与结论

两份评审在关键结论上一致：

- 订单页缺撤单/详情/批量操作（UX P0-1 = TR-05 = REQ-04/05）。
- 策略详情动作过多、语义冲突、确认不一致（UX P0-3 = TR-13 = REQ-13）。
- 应急/只减仓缺影响面与进度（UX P0-2 = TR-13 的一部分）。
- 数据新鲜度与快照覆盖不足（UX P0-5 = TR-08/11 = REQ-10）。
- 行情只有全局“新鲜”布尔，缺逐柜台/逐合约（UX P1-12 = TR-19 = REQ-12/10）。
- 订单/成交/策略列表不实时（TR-07/14 = REQ-15/16）。
- 900px 功能性损坏与列错位（UX P0-4/P0-6，交易员评审未覆盖）。

差异点：

- 交易员评审更关注**盘前就绪判定、拒单可见、限仓额度、收盘检查**；
- UX 评审更关注**信息架构、设计系统、响应式、格式化与颜色语义**；
- 两者都认为 B（quantlink-trading `/product_management/check`）的“KPI + 主表 + 右侧明细 + 常驻应急”骨架更好，但 B 缺交易安全护栏与收盘能力。

**目标形态：B 的骨架 + A 的内核 + 一套统一设计系统。**

## 3. 目标形态

### 3.1 信息架构（5 组 ≤16 项）

```text
总览
├─ 交易驾驶舱
└─ 风险与敞口

交易
├─ 期权链
├─ 手工交易
├─ 订单与成交
└─ 交易日历

策略
├─ 策略中心
├─ 指标中心
└─ 执行默认

数据与接入
├─ 柜台与账户
└─ 合约与费率

运维与审计
├─ 运行与监控
├─ 告警中心
├─ 审计与审批
├─ 任务调度
└─ 收盘快照
```

职责重叠按 UX 评审 §5 处理（执行拓扑/系统监控合并、消息/系统告警合并、持仓三类拆分实时/日终）。

### 3.2 驾驶舱一屏（B 骨架 + A 内核）

```text
┌ 顶栏：环境 | 柜台 2/3 在线 | 行情最差龄 | 交易日时钟 | 只减仓 | 应急 ┐
├ 阻塞条（仅当存在）：拒单 12 · 风控不可用 · ag2612 行情 8s 过期 · 对账差异 2 ┤
├ KPI：发单中 4 | 停机 1 | 异常 1 | 委托 23 | 成交 18 | 拒单 5 | 净敞口 1.2M | 保证金 32% ┤
├ 主表（策略）：状态灯 | 策略 | 柜台/账户 | 腿/合约 | 持仓 | 挂单 | 当日 PnL | 最新 tick 龄 | 操作 ┤
│   └ 行内展开：挂单/成交/拒单 + 单笔撤单 + 原因
├ 右栏 Tab：挂单 | 成交 | 持仓 | 账户 | 告警（选中策略作用域）
└ 底部流：成交/拒单/告警（可暂停、可过滤）
```

- 状态灯只用一个 `runState`：`UNDEPLOYED / INACTIVE / STARTING / ACTIVE / DEGRADED / STOPPING / STOPPED / ERROR / HALTED`。
- `desired/actual/lastOrderAt/lastQuoteAt` 只放 tooltip 或运维页。
- 颜色：灰=未参与、绿=在发单、琥珀=降级、红=不能交易；盈亏红涨绿跌可配置，状态色与方向色分离。
- 刷新：WS 事件 2s 内更新；行情龄逐合约；断线红条 + 数值降级。

### 3.3 统一组件（设计系统）

| 组件 | 用途 | 关键约束 |
|---|---|---|
| `PageHeader` | 标题/环境/主操作 | 标题独占一行，≤2 动作 |
| `FilterBar` | 筛选 | 独立一行，≤6 控件，chip 展示活跃条件 |
| `DataTable` | 所有表格 | 内部横向滚动、sticky 表头/关键列、行高 36/40、数字右对齐 |
| `StatusChip` | 单一状态 | 中文主标签 + code tooltip；9 态色 |
| `FreshnessBadge` | 数据龄 | `3s / 2m18s`；>阈值灰化 |
| `DangerousActionDialog` | 危险动作 | 动作+对象+环境+账户+影响数量；删除需输入 ID |
| `AsyncState` | 空/加载/错误 | 三态互斥，错误可重试 |

格式规范沿用 UX 评审 §6.5（价格按 tick、金额 2 位、时间 CST、ID 可复制、分页中文）。

## 6. 风险与未决

1. **B 无运行实例**：对比基于源码，像素级对比需环境与只读账号。
2. **限仓数据来源**：按 AGENTS.md，必须由运行体上报；W2-4 依赖 Agent/runner 改造，不能前端现算。
3. **状态 9 态**：需要 Agent/ORS/runner 统一上报口径，先定义映射表再改 UI。
4. **告警指纹**：与刚完成的 `reason_code` 去重合并（fingerprint 可复用 code + 合约/方向）。
5. **红涨绿跌**：默认按国内习惯，提供偏好开关；需产品确认默认值。
6. **导航合并**：会改变用户习惯，需保留旧路由重定向与深链。
7. **环境不稳定**：控制面被另一对话重启、宿主机高负载，会干扰视觉/E2E；重试一次并记录。

## 7. 建议立即启动

**Wave 0（W0-1…W0-6）+ Wave 1 的 W1-1/2/3/4**，因为：
